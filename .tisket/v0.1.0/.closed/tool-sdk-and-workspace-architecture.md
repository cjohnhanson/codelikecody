Restructure codelikecody into a Cargo workspace with a shared SDK crate that
defines traits for tools in the ecosystem. Tools (tisket, missouri) implement
these traits. clc orchestrates them.

## Design Principles

codelikecody is an ecosystem of tools with great interoperability that can also
operate standalone. clc is the integration layer — a single binary that mounts
the other tools as subcommands. You can use tisket without missouri, missouri
without tisket, and either without clc, but clc needs both.

## Workspace Structure

```
codelikecody/
  Cargo.toml          (workspace)
  clc/                (main binary — orchestration, hooks, lifecycle)
  clc-sdk/            (shared traits and utilities)
  tisket/             (lib + bin — standalone or mounted in clc)
  missouri/           (lib + bin — standalone or mounted in clc)
```

## Subcommand Mounting

`clc tisket <subcommand>` and `clc missouri <subcommand>` expose the full CLIs
as subcommands. Each tool exports its clap `Command`/`Cli` struct from lib.rs.
The standalone binaries become thin wrappers around the same entry point.

`clc tisket issue list` works the same as `tisket issue list`.

## Three Kinds of Text

### help (indicative)

Standard `--help` output. Reference documentation. Describes what commands exist,
their syntax, their flags. Generated by clap. Available at every level of the
subcommand tree. This is how progressive disclosure works — the agent uses
`--help` to learn more about specific commands as needed.

### prime (imperative)

Directives for agents. Not offering information — asserting requirements.
"You must use tisket to track work. Do not work on untracked items."

Each level of the subcommand tree can have its own prime:
- `clc prime` — workflow enforcement requirements
- `clc tisket prime` — issue tracking requirements
- `clc tisket scratch prime` — scratch/memory requirements
- `clc missouri prime` — testing requirements

clc orchestrates which primes to inject and when, mapped to the agent lifecycle
(SessionStart, periodic reinforcement, etc.).

### docs (diataxis)

Full documentation bundled in the binary via `include_str!()` of markdown files.
Covers all four Diataxis quadrants:
- **Tutorials**: Learning-oriented. "Getting started with tisket."
- **How-to guides**: Task-oriented. "How to write a missouri test."
- **Reference**: Information-oriented. Technical details beyond --help.
- **Explanation**: Understanding-oriented. "Why the phase system exists."

Accessible via `clc docs`, `clc tisket docs`, etc. The binary is the single
source of truth for its own version. No external docs site needed.

## Agent Detection

`CLAUDECODE=1` is already set by Claude Code in the shell environment. The SDK
provides:

```rust
pub fn in_agent_context() -> bool {
    std::env::var("CLAUDECODE").is_ok()
}
```

When in agent context: output plain markdown (agents read it natively).
When in terminal: use termimad for pretty rendering.

This applies to all output — help, prime, docs, status.

## Status Reporting

Each tool implements status at two levels:

- **basic**: One-liner summary. Used for periodic context reinforcement.
  e.g. "tisket: test-feature (in_progress), 3 open in v0.1.0"
- **full**: Complete state dump. Used at SessionStart on a feature branch.
  e.g. full tisket body including scratch section, missouri test results by
  state, all open issues by status.

## SDK Traits

```rust
trait ClcTool {
    fn prime(&self) -> String;
    fn status_basic(&self) -> String;
    fn status_full(&self) -> String;
}
```

Docs and help are handled by clap and `include_str!()` respectively, not traits.

## Context Injection Matrix

clc maps trait calls to the agent lifecycle × workflow state. See README.md for
the current matrix. The SDK defines what tools provide; clc decides when to call
each method based on the hook event and current phase.
